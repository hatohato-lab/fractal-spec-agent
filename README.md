# fractal-spec-agent

要件・Issue・問題意識から、**フラクタル構造の設計書**（枠1枚→要素→また枠）と**学習の層**（用語集）を生成するエージェント ＋ 構造を機械検査するオラクル。
Generates fractal design docs (one frame → elements → frames again) with a built-in learning layer, verified by a deterministic document-structure oracle.

## 入力と出力（これだけ知れば使える）

| | 内容 |
|---|---|
| **入力** | やりたいこと・悩み・要件を書いたもの。**形式は何でもよい**（テキスト・PDF・Excel・画像・複数ファイル可。粗くてよい） |
| **出力** | 読める設計書一式（1枚だけ読めば全体が分かり、分からない所だけ開ける）＋入力に足りない観点の一覧。1枚のHTMLにもできる |

## 背景

AIは一晩で大量に作れるが、人間が一度に把握できる量は変わらない。
この乖離を埋めるのは「ズームできる設計書」——最上位の1枚で全体が見え、
分からない要素だけを開くと、同じ形式で詳細が展開する。覚えた枝は開かなくてよい。
開く場所が減っていくこと自体が、理解の進捗になる。

## 中心の考え方

「分かりやすさ」は主観でも、**分かりやすさを支える構造は機械検査できる**——
ただし保証するのは**構造まで**。内容の正しさ・分割のセンスは保証しない（見本の要素7_限界に明記）。
行数などの閾値は編集上の既定値（`eval/corpus/rules.json` で変更可能）：

| 規則 | 内容 | 根拠 |
|---|---|---|
| R1 | 1ファイル45行以内 | 1画面＝認知の1単位 |
| R2 | 枠の表は2〜9行 | 人が保持できるチャンク数（7±2） |
| R3 | 全ノード同形式 | 形式を学ぶのは1回でよくなる |
| R4/R5 | リンク切れ・孤児ゼロ | ズームの経路が壊れない |
| R6 | 専門用語は用語集に定義必須 | 設計書が学習を内蔵する |
| R7 | 図はPlantUMLを対象で選ぶ・横向き禁止 | 骨組みと部分の関係は図でしか伝わらない |
| R8 | 役割ごとのフォルダに置く | フォルダ名を見ただけで何の文書か分かる |
| R9 | AIの推定は 03_推定/ に隔離・全行に未確認印 | 確認されていない情報を本文に混ぜない |

## 出力の配置

```
出力先/
├── 00_枠.md            入口。ここだけ読めば全体がわかる
├── 00_入力の不足.md     入力そのものの点検結果
├── 01_設計/            設計の本体（要素と、その下の階層）
├── 02_学習/用語.md      学習の層
└── 03_推定/推定.md      AIが推定した補完候補の隔離場所（不足があった場合のみ）
```

## 入力の不足を先に出す（--gaps）

大抵の要件定義には、書き手も読み手も気づかない欠落がある。
書かれていないものは形を持たないため、何度読んでも見つからない。
そこで「あるべき観点の一覧」と入力を機械で突き合わせる。

```bash
python eval/oracle.py --gaps 要件メモ.md
```

```
## 見当たらない観点（8観点中 3件）

★ 前提     この計画は、何が成り立つ前提で立っていますか。それは確認済みですか
   代替案   ほかにどんな進め方がありますか。それを選ばない理由は何ですか
   失敗時   うまくいかなかった場合、次にどうしますか
```

観点は 目的／完了条件／前提／制約／現状／関係者／代替案／失敗時 の8つ（`eval/corpus/input_checklist.json` で編集可）。
★は 目的・完了条件・前提 ——欠けると設計書全体が崩れるもの。

**この機能は不足を埋めない。** 何が無いかを示すところまで。
確認されていない前提を本文に紛れ込ませないため。
語で探すので、別の言い回しは取りこぼす。だから「無い」ではなく「見当たらない」と出す。

## 不足の推定（03_推定・R9）

埋める候補を作るのは生成エージェントの仕事。**入力の点検直後と、設計書が出来上がった後の2回**、
欠けた観点への推定を行う。

ただし推定は本文には書かず、`03_推定/推定.md` に隔離する（全行に「未確認」の印）。
生成の途中でイエス/ノーの確認は取らない——**確認は対話ではなく、置き場所で分ける**。
エージェントは最後まで完走し、人間は後から 03_推定/ を眺めて、採用する行だけ本文へ写して「採用済」にする。
「推定が本文に混ざっていないか」は R9 が機械検査する（本文に【推定】タグが出たら違反）。

## クイックスタート

必要なもの：Python 3 のみ。**リポジトリのルートで実行**。

```bash
python eval/oracle.py            # お手本の設計書を採点 → PASS
python eval/oracle.py --selftest # オラクル自身を検証（37項目） → PASS
python eval/oracle.py --check <フォルダ>   # 自分の設計書を採点
python eval/oracle.py --gaps <入力ファイル> # 入力に何が書かれていないかを出す
python eval/oracle.py --html <フォルダ>    # 設計書を1枚のHTMLに連結（index.html）
```

## HTML1枚出力（--html）

設計書ツリーをリンク順に連結し、`index.html` を出力する。
.md へのリンクはページ内アンカーになり、1枚のままズームの経路をたどれる。
PlantUML はレンダリングせず**ソースのまま**埋め込む（外部サーバに依存しないため。
描画は VSCode の PlantUML 拡張や PlantUML サーバに貼れば見られる）。

## オラクルの信頼性（--selftest・37項目）

- お手本と最小ツリーが合格すること（誤検出ゼロ）
- わざと壊した見本**12種**（長すぎ・枠過大・戻るリンク欠落・リンク切れ・孤児・用語未定義・図なし・横向き図・配置違反・入力点検なし・推定の本文混入・印なし推定）を、**それぞれ正しい規則として**検出すること（1見本1違反で判別まで検証）
- 入力点検が、十分な入力では欠落0、薄い入力では前提・代替案・失敗時を検出すること
- HTML出力が、全ノードを1枚に含み、.mdリンクを残さずアンカー化すること

## 系譜

自作AIエージェント集（評価駆動開発の実証）の一つ。オラクル種別＝**文書構造検査**（新型）。
発想の実証実験：この構造の設計書は、人間の怒りと修正の往復から生まれた実運用の型を一般化したもの。
